# 兼容性：SnowLink 能做什么、做不到什么

一句话：**动作面 213 个全部登记，实现按底层能力如实标注，协议行为逐条对齐。**

| 项 | 数量 |
|---|---|
| SnowLuma 2.2.1 注册的动作 | **213** |
| SnowLink 注册的动作 | **213**（一个不少，全部在 `snowlink/contract.py`） |
| 真能执行的 | **17**（文本收发 + 基础查询 + 撤回 / 禁言 / 踢人 / 历史） |
| 明确拒绝并给原因的 | **196**（`retcode: 1404` + `wording`） |
| 额外扩展动作 | 1（`get_capabilities`，SnowLuma 没有） |

为什么把做不到的动作也注册上：上层框架常会**先探测**（`can_send_image`、
`get_group_member_list` 试一下）。注册了才有机会回「这个动作存在、但这台通道干不了、缺什么」；
不注册只能回 `unknown action`，让人以为接错了实现。

**做不到的一律 `retcode: 1404` + `wording` 说明原因**，不会返回假成功，
也不会把图片降级成 `[图片]` 文字发出去。

## 一、响应信封与 retcode

成功：

```json
{"status": "ok", "retcode": 0, "data": {...}}
```

失败：

```json
{"status": "failed", "retcode": 1404, "data": null,
 "wording": "upload_group_file：群文件/私聊文件接口未实现（需要 ArkLink 的文件通道）"}
```

| retcode | 含义 | 典型场景 |
|---|---|---|
| `0` | 成功 | — |
| `100` | 动作失败 | `get_msg` 找不到消息（`message not found`）、`delete_msg` 找不到可撤回记录 |
| `1200` | 内部错误 | 后端不可达、ArkLink 返回异常 |
| `1400` | 参数不对 | 缺 `user_id` / `group_id`、段数组不合法、HTTP 方法不允许 |
| `1404` | 动作不支持 / 不认识 | 见第三节；路径不在 base 下也是 1404（HTTP 404） |
| `1401` | 未授权 | 仅 HTTP/WS 握手层，`401` + `wording: "unauthorized"` |
| `1413` | 请求体过大 | 仅 HTTP，`Content-Length > 64MB` |

三条容易踩的细节，都与 SnowLuma 相同：

1. **成功响应里没有 `wording` 键**；`data` 可以是 `null`（如 `set_group_ban`）。
2. **`echo` 只在请求带的时候回填**，不会凭空多一个 `echo: null`。
3. 失败时 `data` 固定是 `null`，原因在 `wording`，不要在 `data` 里找错误信息。

## 二、参数校验：文案就是契约

校验在**执行前**做，用的是和 SnowLuma 一样的字段级规则，`wording` 形如 `字段名: 原因`：

| 情况 | `retcode` | `wording` |
|---|---|---|
| 必填没给 | 1400 | `user_id: is required` |
| 类型不对 | 1400 | `group_id: expected a positive integer` |
| 超范围 | 1400 | `duration: must be >= 1` |
| 二选一没给 | 1400 | `send_msg: at least one of group_id, user_id is required` |
| 段数组坏了 | 1400 | `message[0]: unknown message segment type: foo` |
| 动作面里有、但通道做不到 | 1404 | `upload_group_file：<能力缺什么>` |
| 压根不认识 | 1404 | `unknown action` |

数值与布尔是**宽容转换**的：`"123"` 能当 `123` 用，`"true"` / `1` 能当 `true` 用；
但 `"abc"` 不会静默变成 `0`，而是报 `expected a positive integer`。

这条很重要：**先校验、再判断支持不支持**。所以对 `get_group_member_list` 不传 `group_id`
得到的是 `1400 group_id: is required`，而不是 1404——和上游一致。

## 五、message_id：int32 哈希，可以是负数

这不是自增序号，而是和 SnowLuma 一样的**哈希**：

```
message_id = int32_be(sha1(f"{sequence}:{sessionId}:{eventName}")[0:4])  # 0 时取 1
```

- **可以是负数**，所以框架侧别假设 `message_id > 0`，也别拿它当数组下标。
- 同一个 `sequence` 在同一会话里稳定，**重启后不保证复现**（哈希输入含会话 id）。
- 事件里的 `message_id` 与发送返回的是**同一套算法**，所以 Echo 回填、`delete_msg`、
  `get_msg`、`reply` 段能互相咬合。
- `reply` 段只给 `id` 时，会在内存缓存里反查 `sequence`；查不到就按字面值当 `sequence` 用。
- 缓存 500 条，超了丢最旧的；跨重启的 `reply` 会失效。

## 六、消息段

双向转换层与上游的段表逐条对齐，段类型一律小写，长度等字段按 OneBot v11 规范。

| 段 | 发送 | 接收 |
|---|---|---|
| `text` | ✅ | ✅ |
| `image` / `face` / `record` / `video` / `file` | ❌ 1404 | ⚠️ 只以文本形式呈现（ArkLink 目前只给文本） |
| `at` / `reply` | 解析 ✅，发送 ❌ 1404 | ⚠️ 同上 |
| `forward` / `node` | ❌ 1404 | ⚠️ 同上 |
| `json` / `xml` / `markdown` 卡片 | ❌ 1404 | ⚠️ 同上 |
| `share` / `music` / `location` / `contact` | 转成 JSON 卡片再判定 | 同左 |

几条容易忽略的兼容点：

- **判定按整条消息做**：只要有一个段发不出去，整条失败并说明是哪几段，不会截断后发一半。
- **`text: ""` 是兼容占位符**：上游会产出空文本段，SnowLink 按同样规则丢弃，不参与拼接。
- **段对象是扁平的**：顶层字段与 `data` 合并，`data` 优先。所以
  `{"type":"text","text":"hi"}` 与 `{"type":"text","data":{"text":"hi"}}` 等价。
- **CQ 转义**：`& → &amp;`、`[ → &#91;`、`] → &#93;`、`, → &#44;`。
  要发字面量 `[CQ:...]`，用 `"auto_escape": true`。
- **`rps` / `dice` / `shake`** 分别映射到 `face 359` / `face 358` / `poke`，与上游一致。

## 七、事件

| 事件 | 状态 |
|---|---|
| `message` / `private` | ✅ 来自 ArkLink 的 SSE 流 |
| `message` / `group` | ✅ 同上 |
| `message_sent` | ✅ 自己发的消息也推（`private_message_sent` 命名空间） |
| `meta_event` / `lifecycle` | ✅ `connect` / `enable` / `disable` |
| `meta_event` / `heartbeat` | ✅ 30 秒一次，`interval: 30000` |
| `notice` / `request` | ❌ 暂未产出（ArkLink 现在只推消息，不推通知） |

字段与上游 converter 对齐的几处：

- 群消息带 `group_name`、`anonymous: null`、`sender.role`（`owner` / `admin` / `member`）。
- 自发消息 `post_type` 是 `message_sent`，`user_id` 是**自己**，私聊还带 `target_id`。
- 事件内部始终是**段数组**；只有出口按连接的 `messageFormat` 决定要不要换成 CQ 串。
  所以 `message_format: "string"` 时 `message` 是 CQ 串、`raw_message` 同步一致，`array` 时两者都在。
- 除 OneBot 标准字段，多一个 `snowlink` 对象（`seq` / `peer_uid` / `sender_uid` / `source`），
  排查问题很有用，不认识可以忽略。

## 八、四个出口的语义

### HTTP 服务端

- **路径即动作**：`POST /{base}/{action}`，body 为 `{"action":..., "params":..., "echo":...}`
  或直接 `{"group_id":...}`（此时动作取自路径）。路径与 body 都给时**路径优先**。
- `{base}` 之外一律 `404 + 1404 + "not found"`；方法不对 `405 + 1400 + "method not allowed"`。
- `GET` 不带动作 → `{"status":"ok","retcode":0,"data":{"online":true}}`。
- `GET` 查询串每个值**先按 JSON 解析**：`?group_id=123` 得到数字 `123`，不是字符串。
- `POST` 支持 `application/x-www-form-urlencoded` 与 JSON；JSON 坏了回
  `400 + 1400 + "bad request: invalid json"`。

### 正向 WS / 反向 WS

- **角色由路径决定**：`/api` → Api，`/event` → Event，其余 → Universal。
  所以框架连 `/onebot/v11/ws` 得到的是 Universal，动作和事件都能走。
- 连上后 Event / Universal 立刻收到**三帧**：`lifecycle(connect)` → `lifecycle(enable)` → `heartbeat`。
  只发事件不收动作的 Event 连接也一样收三帧，只是发过来的动作被**静默忽略**（不回包）。
- 30 秒一次 ping；连续 90 秒没有任何流量就掐掉半开连接。
- 断开时给 Event / Universal 推 `lifecycle(disable)`。

### HTTP 上报

- 头固定带 `User-Agent: OneBot`、`X-Self-ID`；配了 token 时再带
  `X-Signature: sha1=<hmac_sha1(token, body)>`。
- 上报响应体是 JSON 就当作 **quick operation** 执行：
  `{"reply": "..."}` / `{"delete": true}` / `{"ban": true, "ban_duration": 60}`，
  只在 `post_type == "message"` 的事件上生效。

## 九、鉴权

三种写法都支持，任选其一：

```
Authorization: Bearer <accessToken>
?access_token=<accessToken>
Sec-WebSocket-Protocol: <accessToken>
```

`accessToken` 留空表示不校验——**别在公网地址上留空**。

## 十、与 SnowLuma 的差异清单

1. **不注入 QQ 进程**：QQ 由 ArkLink 那边操作，所以不需要在 Windows 上注入 DLL，
   Linux / 服务器上也能跑（ArkLink 的 Xvfb 方案）。
2. **富媒体暂缺**：当下最大的差异，能力矩阵里写明了原因与「需要什么」。
   这是**唯一**会影响到功能等价的地方，其余协议细节按上面的章节逐条对齐。
3. **没有进程注入页**：WebUI 只有状态 / 网络 / 发送 / 调试 / 事件 / 日志 / 配置。
4. **多账号**：配置文件按 `onebot_<uin>.json` 一份一个账号，与 SnowLuma 一致，
   但一个进程当前只跑一个账号（多实例 = 多个进程 + 不同端口）。
5. **`mode` / `statusCommand` / `historySync` / `notifications`**：
   原样读写保留，暂未实现其行为（写了不报错，但也不产生效果）。
6. **`notice` / `request` 事件**：SnowLuma 会产出十几种（`group_recall`、`group_admin`、
   `group_increase`…），SnowLink 暂时一种都不产出——因为 ArkLink 现在只推消息事件。
   例外：`notice/bot_status` 在连接状态变化时会推。
