# 兼容性：SnowLink 能做什么、做不到什么

一句话：**动作面完整对齐，能力按底层如实标注**。

| 项 | 数量 |
|---|---|
| SnowLuma 2.2.1 注册的动作 | **213** |
| SnowLink 注册的动作 | **213**（一个不少，全部登记在 `snowlink/contract.py`） |
| 真能执行的 | 12（文本收发 + 基础查询） |
| 明确拒绝并给原因的 | 201（`retcode: 1404` + `wording`） |

为什么要把做不到的动作也注册上：上层框架常会**先探测**（`can_send_image`、
`get_group_member_list` 试一下）。注册了才有机会告诉你「这个动作存在、但这台通道干不了、
缺什么」；不注册只能回 `unknown action`，让人以为接错了实现。

**做不到的一律 `retcode: 1404` + `wording` 说明原因**，不会返回假的成功，
也不会把图片降级成 `[图片]` 文字发出去。

## 一、响应信封与 retcode（与 SnowLuma 完全一致）

成功：

```json
{"status": "ok", "retcode": 0, "data": {...}}
```

失败：

```json
{"status": "failed", "retcode": 1404, "data": null, "wording": "delete_msg：撤回需要 ArkLink 的 recall 能力，矩阵里是 false"}
```

| retcode | 含义 | 用在哪 |
|---|---|---|
| `0` | 成功 | — |
| `100` | 动作失败 | `get_msg` 找不到消息（`wording: "message not found"`）、`get_group_info` 查不到群 |
| `1200` | 内部错误 | 后端不可达、ArkLink 返回异常 |
| `1400` | 参数不对 | 缺 `user_id` / `group_id`、段数组不合法 |
| `1404` | 动作不支持 / 不认识 | 见下文分族原因 |

注意：**成功响应里没有 `wording` 键**，`data` 可以为 `null`——这两点都与 SnowLuma 相同，
按严格 schema 校验的客户端不会因此报错。

## 二、真能用的 12 个

| 动作 | 返回 |
|---|---|
| `send_private_msg` | `{message_id}`；`message` 支持段数组 / CQ 字符串，`auto_escape` 也支持 |
| `send_group_msg` | `{message_id}` |
| `send_msg` | 按 `message_type` 或 `user_id` / `group_id` 分派 |
| `get_login_info` | `{user_id, nickname}` |
| `get_status` | `{online, good, time}`，`time` 是实例运行秒数 |
| `get_version_info` | `{app_name, app_version, protocol_version}`，默认 `app_name: "SnowLink"` |
| `get_friend_list` | `[{user_id, nickname, remark}]` |
| `get_group_list` | `[{group_id, group_name, group_remark, member_count, max_member_count, group_all_shut, ...}]` |
| `get_group_info` | 单个群的同上字段；查不到给 `retcode 100` |
| `get_msg` | 消息事件去掉 `post_type` / `self_id`，补 `real_id`；内存缓存最近 500 条 |
| `can_send_image` / `can_send_record` | `{"yes": false}`——诚实的 false，底层确实发不了 |
| `get_capabilities` | **扩展动作**（SnowLuma 没有）：直接透传 ArkLink 的能力矩阵 |

需要严格「顶替」的场合（个别框架按 `app_name` 分支），把 `config/runtime.json` 里
`"appName": "SnowLuma"` 设上即可，其他不变。

## 三、其余 201 个：按能力族给原因

| 能力族 | 数量 | 原因（写进 `wording`） |
|---|---|---|
| `group_mgmt` | 33 | 群管理动作还没落地（ArkLink 能力矩阵里 group_manage=false） |
| `file` | 32 | 群文件 / 私聊文件接口未实现（需要 ArkLink 的文件通道） |
| `qzone` | 26 | QQ 空间接口未实现（需要 ArkLink 的空间通道） |
| `extra` | 23 | 点赞 / 戳一戳 / 分享卡片 / 小程序 / 收藏等扩展接口未实现 |
| `group_query` | 18 | 群资料与成员查询还没接上真实 QQ（roster=false） |
| `face` | 15 | 表情与自定义表情接口未实现（需要结构化消息通道） |
| `friend` | 12 | 好友资料 / 好友管理接口还没落地（需要花名册接口） |
| `album` | 9 | 群相册接口未实现（需要相册通道） |
| `forward` | 7 | 合并转发需要结构化消息通道；现在只能发纯文本 |
| `credentials` | 6 | QQ 登录凭据由 ArkLink 侧的官方客户端持有，OneBot 侧拿不到 |
| `online` | 6 | 在线状态与客户端信息接口未实现；只保证消息收发 |
| `read` | 4 | 没有已读上报通道（read_report=false） |
| `control` | 4 | 进程控制不归本进程管，退出 / 重启请用 systemd 或 start.bat |
| `history` | 3 | 历史消息接口未实现；只有本次运行内的缓冲（`since` 续传） |
| `media` | 2 | 不接管图片 / 语音文件本体 |
| `recall` | 1 | 撤回需要 ArkLink 的 `recall` 能力，矩阵里是 false |

完全不在 213 个里的名字，`wording` 就是 `unknown action`（与 SnowLuma 一字不差）。

## 四、消息段

| 段 | 发送 | 接收 |
|---|---|---|
| `text` | ✅ | ✅ |
| `image` / `face` / `record` / `video` / `file` | ❌ 1404 | ⚠️ 只以文本形式呈现（ArkLink 目前只给文本） |
| `at` / `reply` / `forward` / `node` | ❌ 1404 | ⚠️ 同上 |
| `json` / `xml` / `markdown` 卡片 | ❌ 1404 | ⚠️ 同上 |

判定是**按整条消息**做的：只要有一个段发不出去，整条就失败并说明是哪些段。

要发纯文本里带 `[CQ:...]` 的字面量，用 `"auto_escape": true`。

## 五、事件

| 事件 | 状态 |
|---|---|
| `message` / `private` | ✅ 来自 ArkLink 的 SSE 流 |
| `message` / `group` | ✅ 同上 |
| `message_sent` | ✅（该连接的 `reportSelfMessage` 为 `true` 时才推） |
| `meta_event` / `lifecycle` | ✅ 连接建立时推 `connect` |
| `meta_event` / `heartbeat` | ✅ 每 15 秒 |
| `notice`（群文件、入群、撤回…） | ❌ 暂未产出（ArkLink 现在只推消息，不推通知） |
| `request`（加好友、加群） | ❌ 暂未产出 |

收到的事件里除 OneBot 标准字段，还多一个 `snowlink` 对象
（`seq` / `peer_uid` / `sender_uid` / `source`），排查问题时很有用，不认识可以忽略。

## 六、鉴权

三种写法都支持，任选其一：

```
Authorization: Bearer <accessToken>
?access_token=<accessToken>
Sec-WebSocket-Protocol: <accessToken>
```

`accessToken` 留空表示不校验——**别在公网地址上留空**。

## 七、与 SnowLuma 的差异清单

1. **不注入 QQ 进程**：QQ 由 ArkLink 那边操作，所以不需要在 Windows 上注入 DLL，
   Linux / 服务器上也能跑（ArkLink 的 Xvfb 方案）。
2. **富媒体暂缺**：当下最大的差异，能力矩阵里写明了原因与「需要什么」。
3. **没有进程注入页**：WebUI 只有状态 / 网络 / 发送 / 调试 / 事件 / 日志 / 配置，
   不做「探测登录、加载进程」那套（那是注入方案才需要的）。
4. **多账号**：配置文件按 `onebot_<uin>.json` 一份一个账号，与 SnowLuma 一致，
   但一个进程当前只跑一个账号（多实例 = 多个进程 + 不同端口）。
5. **`mode` / `statusCommand` / `historySync` / `notifications`**：
   原样读写保留，暂未实现其行为（写了不报错，但也不产生效果）。
6. **`notice` / `request` 事件**：SnowLuma 会产出十几种（`group_recall`、`group_admin`、
   `group_increase`…），SnowLink 暂时一种都不产出——因为 ArkLink 现在只推消息事件。
